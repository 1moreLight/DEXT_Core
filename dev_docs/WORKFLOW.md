# Dext 单任务开发流程

> 生效：2026-08-28。本文是开发执行流程的唯一说明。
> 核心规则：**一个任务 = 一个工作包 ID = 一个 worktree = 一个分支 = 一份验收；用户验收通过后才合并 master。**

## 一、为什么这样做

Dext 同时包含 React、Rust、C# 和桌面渲染器，过去按“大阶段”并行推进，容易出现范围混杂、分支互相污染、验收不清和文档状态冲突。

从现在开始，每轮只交付一个用户能独立理解和验证的结果。一个任务不能靠“顺便再做几件事”扩大范围；发现新需求，登记到 ROADMAP，另开下一轮。

## 二、五个真相源

| 问题 | 唯一答案位置 |
|---|---|
| 产品是什么、为什么这样设计 | `PROJECT.md`；具体模型看 `MODEL.md` / `DOCK.md` |
| 全局还有什么、先做什么 | `ROADMAP.md` |
| 当前分支正在做什么、做到哪一步 | `TODO.md` 最后一节 |
| 这一轮怎么验收 | `acceptance/<工作包ID>-<名称>.md` |
| 已知坑与防再犯 | `ERRORS.md` → `errors/` 对应分册 |

发生冲突时：当前代码与 Git 状态 > 已确认的 PROJECT/MODEL 决策 > ROADMAP > 当前 TODO > 历史文档。历史进度文档不得覆盖当前状态。

## 三、状态只有六种

| 状态 | 含义 |
|---|---|
| `排队` | 有价值，但还没决定何时做 |
| `下一项` | 唯一推荐的下一个工作包；全项目最多一个 |
| `开发中` | 已有独立 worktree/分支；默认全项目最多一个 |
| `待验收` | 已提交、自测通过，尚未得到用户确认；禁止合并 |
| `已完成` | 用户验收通过，已合并 master 并清理工作分支/worktree |
| `受阻` | 无法继续，原因和恢复条件已写清楚 |

`ROADMAP.md` 保存全局状态；`TODO.md` 只保存当前分支的执行步骤，不再兼任产品 backlog。

## 四、一轮开发的固定流程

### 1. 选定一个工作包

- 默认取 ROADMAP 标为“下一项”的唯一工作包。
- 用户可以指定另一个工作包；被跳过的任务留在原状态。
- 开工前把目标压缩成一句话，并写清“不做什么”。
- 如果无法给出独立验收步骤，说明任务仍然太大，必须继续拆分。

### 2. 建立隔离空间

- 从最新 `master` 创建独立 worktree。
- 分支名使用 `feat/<工作包ID小写>-<slug>`；修复可用 `fix/...`，纯文档可用 `docs/...`。
- 一个会话只在自己的 worktree 里运行 Git 命令。
- 主 worktree 只用于查看、合并和清理，不直接开发。

### 3. 冻结本轮范围和验收

动代码前必须完成：

1. 在 TODO 末尾追加当前工作包计划。
2. 新建 `dev_docs/acceptance/<ID>-<slug>.md`。
3. 写明目标、范围外事项、自动检查、人工验收步骤和通过标准。

验收内容可以在开发中因事实修正，但不能为了让失败的实现“通过”而降低标准；需求变化要注明由用户确认。

### 4. 开发与自测

- 每完成一步立即更新 TODO。
- 只改完成当前目标所需的文件。
- 新发现的旁支任务只登记 ROADMAP，不顺手实现。
- 遇到新坑，解决后追加 ERRORS；结构决策追加 PROJECT。
- 查代码先用 CodeGraph；改代码后继续查询前先 `codegraph sync`。
- 按改动层运行对应检查，检查失败不得进入待验收。

### 5. 提交并进入待验收

- `git status --short` 核对清单，只暂存本轮具名文件。
- 自测通过后提交到工作分支。
- ROADMAP 状态改为“待验收”；TODO 技术步骤全部完成，保留一项“用户验收”。
- 对话交付必须说明：工作包、分支、提交、改动范围、自动检查结果、已知限制和人工验收步骤。
- **到这里停止，不合并 master。**

### 6. 用户验收

用户只需给出一种结论：

- `通过`：进入合并流程。
- `不通过 + 现象`：继续在同一分支修复，更新同一份验收文件，再次提交和验收。
- `需求变化`：小范围且仍是同一目标时留在原分支；已经变成另一个结果时，新建工作包和分支。

### 7. 合并与清理

只有用户明确确认通过后才能：

1. 在主 worktree 更新 master 并确认干净。
2. 合并已验收分支；不得夹带其他分支。
3. 必要时在 master 做最小冒烟检查。
4. ROADMAP 标“已完成”，验收文件记录通过日期和合并提交。
5. 将 TODO 当前轮归档到 `TODO-archive.md`。
6. 删除已合并分支和对应 worktree。
7. 把 ROADMAP 中下一个工作包提升为唯一“下一项”。

## 五、标准验收卡

每份独立验收文件至少包含：

```markdown
# <工作包 ID> <名称> 验收

- 状态：草拟 / 待验收 / 已通过
- 分支：feat/...
- 提交：待提交 / <hash>
- 目标：一句话
- 范围外：本轮明确不做的内容

## 自动检查
- [ ] 命令与预期结果

## 人工验收
1. [ ] 用户能照做的步骤
2. [ ] 明确可观察结果

## 通过标准
- 所有必选项通过；没有阻断问题。

## 验收记录
- 待用户确认
```

对话里的验收清单必须与该文件一致，但用户只需要在对话中回复，不要求用户手改 Markdown。

## 六、测试路由

| 改动 | 最低检查 |
|---|---|
| React / TypeScript | `npm run build`；设计模式人工检查深色/浅色 |
| Rust / Tauri command | `cargo check` + 相关测试；必要时 `scripts/start.ps1` |
| C# / `.proto` | `scripts/build.ps1` 后 `scripts/start.ps1`；Player 必须 Release |
| 渲染器 JS/CSS | `node --check main.js` + `scripts/room-preview.ps1`；涉及真桌面再跑 `scripts/start.ps1` |
| Room 应用链 | `cargo test --lib applies_room_wallpaper` + 真机应用 |
| 纯文档 | 链接、工作包 ID、状态、Git 分支和相互引用一致性检查 |

最低检查不是上限；验收文件应按风险补充本轮所需检查。

## 七、并行和中断

- 默认不并行，先完成并验收当前工作包。
- 用户明确要求并行时，每个工作包仍必须有独立 worktree、分支、TODO 小节和验收文件。
- 会话中断后先读 ROADMAP 的“开发中/待验收”项，再进对应 worktree，从 TODO 最后一项继续。
- 不得因为另一个任务着急，就在错误 worktree 中提交、重置或清理。
