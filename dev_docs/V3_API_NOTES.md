# v3 作者 API 核查笔记

> 2026-09-25 起的设计备忘，**不是已发布的 v3 API 契约**。本文件整合当前 master 的代码核查笔记，以及 `docs/V3-API-001-widget-api-draft` 分支的 `dev_docs/V3_API.md` 讨论稿（提交 `bfbb01f`，截至整合时仍待用户验收、未合并 master）。整合只为继续讨论，不表示原分支工作包已验收或 v3 接口已定稿。产品方向见 [V3_IDEAS.md](V3_IDEAS.md)，运行逻辑见 [V3_RUNTIME_MODEL.md](V3_RUNTIME_MODEL.md)，技术风险见 [V3_FEASIBILITY.md](V3_FEASIBILITY.md)。

## 文档与实现现状

独立分支已有 Room v3 Widget API **讨论稿**；当前 master 尚无正式 v3 Schema、v3 SDK 或运行时。正式运行契约仍是 Room v2。现有可对照资料包括 [Room v2 受控系统 API](ROOM_V2_SYSTEM_API.md)、[Widget v2 契约](WIDGETS_V2.md)、[Room v2 作者协议](ROOM_AUTHORING.md)和 [Lively API 调研](LIVELY_API.md)。这些文件分别描述作者能力边界、Widget 权限、作品编写和上游 Player 内部通道；**不能把 Lively 的 JS 函数或顶层 WebView2 消息当成 v3 作者 API**。

### Dext API 的定位（整合分支讨论稿）

Dext API 是给 Room 内 **HTML/CSS/JS 作者**使用的 JavaScript 工具层。作者负责画界面和交互，Dext 提供经过裁剪、授权的数据及动作，并负责与 Windows、Lively 底座和本机用户数据打交道。作者不应直接解析 Lively 注入消息或依赖底层 `postMessage`。AI 生成的作品也使用同一套公开接口、类型和示例。它不是对外网站的 HTTP API，也不直接规定作品文件夹的打包格式。

**2026-09-28 已确认的安全方向：**v3 网页作品只加载随 Room 打包的本地 HTML/CSS/JS，不支持输入在线网址直接作为壁纸。作者可自由控制视觉外观；任何应用/文件/系统数据和动作都必须通过 Dext 公开且受控的作者 API 请求。作品导入检查包和能力声明，真实 WebView2 宿主仍限制导航、资源请求、弹窗、下载和原生消息；权限在宿主侧按来源、身份、参数和输入条件执行，不能凭静态 HTML 扫描判定脚本安全。作者页与 Dext 官方图标/Widget 如何视觉统一但不共享原生权限，仍需设计和验证。

**同日进一步确认：**作者自己的 DOM、样式和动画由作者编写；对 Dext 官方图标、Widget、Desk、受控数据和系统动作，只允许使用 Dext 公开 API，不暴露官方内部 DOM、原始 WebView2/Lively 消息或 Core 对象。作品可以声明图标呈现与过渡意图，Dext 如何把它同步到同一视觉画布需通过原型确定。此处确认的是可访问边界，不预先固定 iframe、Shadow DOM 或其他具体隔离实现。

分支稿以 Widget 创作为叙述重点；我们的 v3 产品目标更广：**Room、Desk、可选 Dock 及其他可视部分都应允许作者用 HTML 定义**。因此作者 API 应服务整个作品，而不是只把现有 Widget API 换一套名称。哪些内容属于同一个 HTML 执行上下文、哪些必须独立宿主，仍需设计。

| 项目 | 当前可核实的状态 | 对 v3 的意义 |
|---|---|---|
| 作者 SDK | [dext-sdk.js](../creator-kit/sdk/dext-sdk.js)、[类型](../creator-kit/sdk/dext-sdk.d.ts)是 protocol 1，公开 `dext.get(capability)`、`dext.subscribe(capability, fn)`、`ready/done/error`；实例有 `kind: scene/widget` | 可复用订阅模型，但需设计 Room 常驻层、Dock 类组件和 Desk 上下文 |
| 只读数据 | [capability-bridge.js](../wallpapers/dext-room/capability-bridge.js)发布 `time.read`、`desk.read`、CPU/GPU/RAM、媒体、音量等裁剪后的快照 | 现有数据源可复用；跨独立 Dock 窗口要另建同步/订阅链 |
| 系统动作 | [main.js](../wallpapers/dext-room/main.js)的官方可信热点接收点击；`action.invoke` 当前限于媒体/音量枚举 | v3 导航、绑定应用启动需要新的独立能力和宿主命令 |
| 几何/占用区 | v2 作者 SDK 没有发布占用区 API；Widget placement 写在 room.json 中 | v3 需新增声明/更新占用区的作者入口及宿主验证；这只影响 Dext 图标/Widget 布局 |
| 用户存储 | v2 Widget KV 仍是未来设想；作者 iframe 用 `sandbox="allow-scripts"` | v3 待办、倒计时持久化需定义本机命名空间与配额 |
| 应用绑定 | v2 桌面启动链仍传 `target/args/workdir`，作者 SDK 不暴露本机绑定 API | v3 应用作者只见绑定 ID/可展示字段，实际路径由 Dext 保存和解析 |
| 原生 Dock 模式 | 作者 SDK 不负责 Windows AppBar、置顶、触边和游戏抑制 | 模式归 Dext 宿主/用户偏好；HTML 作者只设计画面和受控动作 |

现有 v2 Creator SDK 是按能力名读值和订阅的消息通道，能作为 v3 的数据来源与隔离起点；它还不是面向普通作者的完整创作 API。首要任务是把已有能力整理成按用途分组、名称明确、有类型和例子的作者接口，再按真实作品场景增加能力。无需在这个讨论阶段先冻结 API 版本号或最终函数名。

## 发现的文档与实际 SDK 不一致

1. [ROOM_V2_SYSTEM_API.md](ROOM_V2_SYSTEM_API.md)原有 `dext.request("system.media.read")`、`dext.subscribe("system.media.changed", ...)` 示例，但当前 [SDK](../creator-kit/sdk/dext-sdk.js)没有 `request` 方法。实际订阅名是 `now-playing.read`、`system.volume.read` 等；作者模板也调用 `dext.subscribe("now-playing.read", ...)`。本轮已把 v2 文档示例改为真实 SDK；v3 不应复制原有方法名。
2. v2 系统 API 与 Widget 契约原写“按内容哈希重新授权”；当前 [Rust 授权审阅](../tauri-ui/src-tauri/src/lib.rs)的 `room_fingerprint` 和 [Core 授权复核](../lively-core-separation/src/Lively/Lively/Core/Wallpapers/WebWebView2.cs)实际对源 `room.json` 字节求摘要，并没有覆盖每个 HTML/JS/CSS 文件。本轮已修正 v2 文案；v3 必须单独设计“作品版本/可执行资源摘要/用户授权”的一致性。
3. [ROOM_AUTHORING.md](ROOM_AUTHORING.md)原写“WidgetHost 尚未实现视觉运行”，与当前 [main.js](../wallpapers/dext-room/main.js)的 `mountWidgets` 不一致。本轮已改为当前实现状态，避免作者或 AI 从历史文字推断运行能力。
4. SDK 初始化的 `session.permissions` 当前取自作者在清单中声明的数组；运行时 `registerCapabilityFrame` 才按本机授权过滤可发布数据。作者不应通过该数组推断某项能力已经批准。v3 建议把 `requested` 与 `granted` 的含义分清，或直接提供可观察的能力状态。
5. [dext-sdk.d.ts](../creator-kit/sdk/dext-sdk.d.ts)把 `action.invoke` 与只读能力放在同一个 `DextPermission` 联合类型，`get/subscribe` 因此也接受它；但当前能力桥不发布 `action.invoke` 快照。v3 类型应把“数据订阅”与“可请求动作”分开，减少 AI 写出无效调用。

## 建议先定义的 v3 API 面

这里是**功能分层**，不是最终函数名或 JSON 格式。作者最好只面对一份简短、版本化的 SDK；宿主↔Player↔Core 的 IPC 是内部协议，不交给作品作者。

| 作者需要表达什么 | 候选能力形状 | 数据/动作由谁拥有 | 仍需决定 |
|---|---|---|---|
| 当前 Room/Desk 与主题状态 | 订阅 `desk` 快照和 Desk 对常驻 Room 组件的展示参数 | Dext 状态管理器 | 切页动画中何时发布；是否给非活动 Desk 数据 |
| CPU/GPU、时间、媒体、音量 | 延续裁剪后的订阅 | Dext 缓存与权限桥 | 各组件频率、隐藏/暂停时更新策略 |
| 作者图层与占用区 | 可按图层或 HTML 元素标记不允许放置的区域；运行时报告几何及 viewport/layout revision | 作者声明意图，Dext 测量/校验并用于图标与普通 Widget 避让 | 图层角色如何表达；元素标记还是显式矩形；失效/无空位回退 |
| 切 Desk | 声明导航热点或申请 `desk.navigate` | 官方可信输入层执行 | 普通 Scene 是否可申请；键盘范围 |
| 显示/启动用户绑定应用 | 订阅经裁剪的全局+Desk 列表；热点提交绑定 ID | Dext 本机绑定库与可信输入层 | 列表重复、顺序、缺失绑定反馈 |
| 风格化动作入口 | Room 分享按钮外形、位置和可绑定槽位；可附带通用 Dext 操作；应用、文件、网址等具体外部目标由使用者在 Dext 绑定 | Room 提供可分享入口；Dext 管理个人目标、授权和执行 | 槽位如何命名/绑定；未绑定时如何显示；哪些内置操作可随作品声明 |
| 应用图标呈现 | 默认图标由 Dext 提供；作品可用 HTML 绘制，创意工坊可提供软件对应图标资源 | Room 自行定义 Desk；Dext 保管本机应用绑定、启动权限、图标皮肤及用户选择 | 自绘图标的位置/拖动/命中如何与默认层切换；图标资源如何匹配本机软件；不同 Room 的 Desk 如何对应 |
| 生活 Desk 待办等本机数据 | 有配额的作品/组件命名空间存储 | Dext 用户数据目录 | 能力审批、备份、卸载和跨 Desk 共享 |
| 原生 Dock 显示模式 | 作者声明所需呈现区域/入口；Dext 统一设置控制自动隐藏或常驻 | Core 原生窗口管理 | 模式不随 Room 切换；v3 首轮同屏一个独立窗口，默认停靠底部。宿主控制窗口与工作区占位尺寸，作者 HTML 不可自行扩大；高度上限待定。桌面按钮可分散在 HTML 场景中 |

2026-09-26 入口模型补充：用户希望把图标启动、壁纸自定义按钮启动都纳入交互层。可把“用户本机目标绑定”和“场景中的启动入口”分开：入口可以是默认/换肤/自绘图标，也可以是作者留出的 HTML 按钮；两者都引用 Dext 管理的绑定 ID，由宿主核验并执行。分享包只含按钮槽位和外观，不含具体软件名要求或本机路径。用户确认两类入口可在同一 Desk 共存并指向同一目标：情景背景中的多个按钮可分别配置，普通图标还能放在更上方。交互层是职责语义，不是固定的唯一 DOM 平面；按钮所在的有效占用区仍阻止普通图标/Widget 放置。

2026-09-26 绑定界面补充：用户选择进入 Dext 配置背景按钮。作者 API 应让 Dext 在安装/预览时枚举作品声明的全部按钮，而不仅扫描当前 Desk 的 DOM：每个按钮有稳定 ID、归属 Room/Desk、编辑器可读名称和当前/默认动作；运行时报告该按钮当前的 HTML 命中区域和可见状态。Dext 编辑器按 Desk 展示同一清单并可在预览中定位/高亮，未配置动作的按钮也列出。分享包只含作者声明，不含用户选的本机目标。分享作品不建立新版覆盖旧版的版本链；重复导入同一分享包创建独立 Room 副本，不复用已有副本的个人配置。清单的具体格式、动态生成按钮，以及多个副本并存时的 ID 作用域待设计。

用户纠正：不要在作者 API 或编辑器里先分“切页按钮”“启动按钮”等等级/类型；按钮先统一存在，功能是按钮的动作属性。候选动作包括 Desk 导航、启动 Dext 本机绑定、媒体控制、作品内部交互和未设置。Dext 可以按动作在内部进行不同的能力校验和参数编辑，但统一呈现按钮列表与创作入口。默认图标可复用这一动作概念，另有拖动/放置语义。用户确认作者预置的动作可在 Dext 中改为另一种受支持的动作；作者默认值随 Room 分享，用户覆盖值仅留本机。`dext.exit` 是内置动作，含义为彻底关闭 Dext 并回到普通 Windows 桌面；触发后必须由 Dext 显示确认，作者 HTML 的提示不能代替。具体退出/恢复流程尚待设计。

2026-09-27 简单路线图的 Dock 方向为“外观→交互→Desk”。用户确认外观下载包含作者定义的可点击区和数据展示槽位/锚点，并提供响应式位置；交互节点按 Desk 给这些区域配置动作和显示数据类型，用户不用重新绘制区域。同一左中右三栏外观在 Desk 1 显示 CPU／时间／GPU、Desk 2 显示倒计时／时间／日期，是复用外观而变化交互数据的例子。作者契约需要稳定区域 ID 与布局规则；应用路径、个人动作覆盖值和个人倒计时设置不进入外观包。区域能否同时承担显示和点击、一个区域关联多个动作的规则仍需定义。

2026-09-28 D06 补充：展示槽不声明限制用户可选数据源的类型白名单；Dext 交互编辑器允许把任意已开放的数据源接入槽位，作者 HTML 负责解释数据并绘制外观，宿主不按槽位形状自动把日期、待办等转换成百分比。作者示例数据可帮助预览，但不是选项限制。GPU 百分比换为有效的事件提醒文字时，数据并未“不可用”，只是原外观可能没写对应呈现。数据确实缺失、无权限或明确渲染失败时，默认保留仪表盘等静态外框，只隐藏受影响的读数/内容，不覆写大号“不可用”；原因可在编辑器/试验台显示。任意 HTML 的视觉适配不能仅靠宿主自动判定，需作者处理或通过试验台检查；外框和数据内容如何分离成可控区域留接口设计。

2026-09-27 游戏版外观新提议：作品可附一份由作者制作的只读 XAML 视图，与桌面 HTML Dock 共享语义上的数据槽 ID 和经裁剪的数据快照，但游戏视图不获得按钮动作、应用路径或其他特权。XAML 的允许元素/属性/资源、槽位绑定方式、更新频率和加载失败回退都要单独定义。固定 Dext Game Bar Widget 宿主加载作者片段是待验证的交付候选，不是已可用的作者 API；Game Bar 的 UWP/XAML 与 Dext 当前 WebView2/HTML 沙箱不同，不能直接照搬现有 JS SDK。

用户随后确认：游戏版 XAML 由 Room 作者另行提供，不包含在下载的 Dock 外观模板中；路线图另有独立节点。游戏版是否复用桌面逐 Desk 的数据槽配置尚未确定，所以前段“共享语义上的数据槽 ID”只表示可用同一批 Dext 受控数据，不预设配置复用或相同槽位布局。

作者将仍可自由编写 HTML/CSS/JS。上述 API 仅定义 Dext 需要知道和授权的部分，避免把所有作品限制为固定样式。**可选常驻 Room HTML**与**独立顶层 Dock HTML**可能是两个运行实例：作者代码可共享资源，但两者不能共享同一 DOM 或直接互相访问；通过宿主同步 Desk 快照与用户绑定状态。

用户提出用“图层”重新理解占用区。候选解释是：图层描述画面组织和叠放，可由作者在其中标记哪些元素/范围要避让 Dext 图标与普通 Widget；Dext 再把标记转换为可校验的几何占用区。显示在上层、接收点击、禁止放置是三种不同语义，不能只靠 CSS 层级或像素透明度自动推断。作者是否操作整个图层、标记单个 DOM 元素或直接画区域，留给试验台比较。

用户给出的图层例子包括**背景层、互动层、Dock/Widget 层**。这应先作为作者组织作品的概念，而非立即冻结若干系统层级或强制每层一个网页。API/宿主需要区分图层的生命周期（Room 常驻或逐 Desk）、叠放、输入和占用属性；一个互动按钮也可能直接位于某个内容层内。真正置顶于其他应用的 Dock 由原生窗口承载，不能从同一桌面网页靠 `z-index` 升上去。

用户认为八类图层过细，已收成 **Desk 背景层、交互层、Dock 层**，另有试验台专用的占用/命中检查视图，见 [V3_IDEAS.md](V3_IDEAS.md)。用户明确保留 Dock 名称。三类层是作者在代码里组织场景的语义，不是 PS 式拖动界面或固定的 DOM 容器；按钮仍可嵌在背景或 Dock 里，交互、占用、权限及 Room/Desk 生命周期各自独立。

用户进一步确认 v3 需要支持**一张持续运行的网页里的连续 Desk 视角**：同一个仪表盘在 Desk 1 缩在底部作为 Dock，切换时连续推近，到 Desk 2 成为可交互的全屏主画面。这是对作者 API 的生命周期要求：共享场景不因 Desk 切换而销毁，Desk 状态和过渡进度可被作者感知；占用区、点击范围和 Dext 图标放置须跟随画面变化并有明确的过渡处理。独立原生 Dock 窗口若参与这种视觉连续性，需另行设计跨窗口交接，不能假定 DOM 可直接搬运。
用户确认视觉控制边界：创作者可以定义切 Desk 的画面移动、缩放和共享元素动画；缺省使用 Dext 的基本动画。Dext 管理状态、图标/Widget 同步和结束收敛；作者获得的是视觉控制权，不是本机系统权限。作者 API 仍需说明共享时间轴、完成/失败通知以及默认动画如何启用。
用户再补充：一个 Dock 可以在所有 Desk 始终存在且不变；汽车仪表盘例子则是始终存在但会随 Desk 改变。API 需要分开表达对象是否跨 Desk 保留、保留时是否对 Desk 状态作出视觉/数据反应。它们不是必须分成不同“组件等级”；单看作品文件属于 Room HTML 还是 Desk HTML，不足以说明对象行为。
用户随后澄清：同一元素在 Desk 1 可以扮演 Dock 层，在 Desk 2 扮演背景层；层是**随 Desk/过渡状态变化的角色**，不是固定类型。仪表盘在 Desk 2 占满画面后仍能切回。用户倾向 Dext 不在最前台时可能暂停 Desk 切换，因此连续推近首先针对 Dext 桌面正在交互的场景；暂停的具体条件和恢复方式尚未定稿。这个例子本身不要求跨原生 Dock 窗口和桌面网页搬运 DOM。普通最大化软件上的 Dock 显示模式仍是独立原生窗口问题。

2026-09-26 用户补充：Desk 图标/普通 Widget 应像放在同一逻辑画布的对应 Desk 区域里，翻页时跟随该区域滑动。作者 API/宿主因此不能把 Dext 图标固定成与场景无关的视口叠层；需要让用户内容参加同一过渡坐标系。跨 Desk 的仪表盘则作为共享元素独立变形，从 Desk 1 的 Dock 过渡到 Desk 2 的背景/交互主画面。“画布”不等于必须使用 HTML `<canvas>` 元素。用户进一步提出把图标也放入统一 HTML 场景，图片/视频只是场景素材；图标 DOM 由作者直接掌握还是由 Dext 在同一画面中受控绘制，仍需定界。

2026-09-25 进一步讨论：用户希望**默认继续使用现有 Dext 图标**，同时允许作品开放 HTML 自绘；创意工坊可以下载某个软件对应的图标。这是可选创作能力，不要求每个 Room 重做图标。图标图片或模板可替换，应用绑定、授权和启动仍归 Dext。图标资源是单个、成套还是自动匹配，以及自绘图标能否自由移动，尚未定稿。

用户随后明确：下载的图标皮肤及个人选择属于 **Dext 本机用户数据**，不放进 Room 包；同一用户可在不同 Desk 选择不同皮肤。每个 Room 自己定义任意名称和数量的 Desk；Dext 不预设“游戏”“生活”等 Desk 类型。跨 Room 如何对应这些 Desk 以及何时沿用选择仍需设计；不能把名称或第 1/2 页下标天然视为稳定身份。此前将举例名称理解成 Dext 固定 Desk，是错误推断。

进一步的候选模型是 **Dext 统一管理个人目标，Room/Desk 只提供呈现入口**：用户先在 Dext 管理应用、文件夹、网址等目标，再决定它们在 Room 的哪些 Desk 上出现。默认类苹果图标继续可用；风格化 Desk 可以提供 HTML 按钮、仪表盘控件或其他外形，而不要求所有入口都是图标。分享包只携带视觉设计、可绑定槽位，以及经允许的通用 Dext 操作（如切 Desk）；**不携带作者指定的具体应用、文件、网址，也不携带用户的本机绑定**。后者全部留在 Dext 个人数据中。作者 HTML 不能携带本机任意路径或绕过可信点击。应用目录、Desk 展示分配、图标皮肤和 HTML 入口应作为不同概念设计。

### 与 Room v3 同时确定的宿主边界（整合分支讨论稿）

| 边界 | 作者 API 要表达什么 | Dext 宿主要保证什么 |
|---|---|---|
| 组件身份与生命周期 | 普通 Widget、常驻 Room 组件、特殊 Dock 组件能读哪些上下文；Desk 切换、暂停/恢复、视口变化和销毁何时通知 | 常驻实例切 Desk 时不重建；逐 Desk 实例按规则挂载/释放；旧 Desk 的迟到消息不能覆盖新状态。权限差异不能只靠同页 HTML 标签区分 |
| 数据与动作 | 只读订阅和授权动作分开；不可用或拒绝时有明确结果 | 校验作品声明、组件身份与实际授权；切 Desk、启动应用等动作由可信真实输入触发，作者脚本不能伪造点击证明 |
| 应用启动 | 作者只使用用户在 Dext 创建的应用绑定 ID | Dext 在本机解析绑定并决定是否允许启动；作品文件和公开 API 不接触可执行文件路径 |
| 本机目标的可信输入 | 作者入口可请求打开用户已绑定的应用或文件 | 只响应使用者真实的鼠标/键盘操作；宿主拒绝脚本定时请求、合成点击和作者自报的输入证明，具体核验机制待实机验证 |
| 入口位置与权限 | 同一按钮动作可在背景、Dock 或普通 Widget 中呈现 | 使用同一能力与授权规则；Dock 的原生窗口形态不赋予额外的数据或启动权限 |
| 布局与点击 | 可申报多块占用区；可点击区与占用区分别表达 | 校验坐标、数量、面积和布局时序；预览与桌面共用几何规则。占用区避让 Dext 图标与普通 Widget，但不会自动改变 Windows 最大化窗口工作区 |
| 本机数据 | 待办等作品数据按作品/组件隔离读写，明确容量、删除和失败反馈 | 用户数据留在本机并与可分享作品资源分离；不依赖沙箱页面的 `localStorage` 长期可用 |

原生 Dock 的置顶、自动隐藏、游戏全屏隐藏和工作区占位属于 Windows 宿主能力。HTML 可以定义外观和受控按钮，但自身不能决定窗口层级。这里区分“点击区”和“占用区”，**不表示顶层 Dock 必须点击穿透**；首轮可先验证矩形原生窗口与实际按钮体验。

## 对 AI 创作目标的检验

只公布 API 名称还不够。给外部 AI 的 v3 作者包至少要同时包含：一页“能做什么/不能做什么”、机器可校验的 manifest、与实际运行 SDK 一致的 TypeScript 类型、最小“有 Room HTML”和“无 Room HTML”样包、双 Desk 汽车仪表盘样包、权限拒绝/绑定缺失/几何越界的明确错误，以及无需真正应用壁纸的本地试验台。现有 v2 [Creator Pack](../creator-kit/)和 [export_ai_context](../tauri-ui/src-tauri/src/creator.rs)提供起点；所有例子必须使用真实 SDK 方法，不应只从自然语言设计稿生成。

每项正式能力至少写清用途、最小可运行示例、数据形状及单位、权限、更新时机、拒绝/不可用结果，以及预览和真实桌面的差异。配套类型定义、完整作品模板和常见错误说明。创作链是 **AI 或作者生成离线作品 → 导入/校验 → 预览和调试 → 真实桌面验收**；预览使用与生产一致的 SDK、消息规则和布局计算，能模拟 Desk 切换、尺寸变化、数据缺失和权限被拒。真实点击、WorkerW 输入及原生 Dock 窗口行为仍需 Windows 实机验证。

分支讨论稿建议先验证双 Desk 的常驻仪表：通过公开 API 读时间和音频，正确处理切 Desk、暂停和销毁，并让预览与真实桌面一致；之后再加入存储、多块占用区和特权动作。这个顺序适合作为**数据订阅原型**，但不足以单独验证我们想要的“HTML 自由布局”：在决定 v3 最小闭环时，还应尽早验证占用区、导航和有/无 Room HTML 两种作品结构。

下一步若开始正式 API 设计，宜先决定 **作者如何声明可信按钮、占用区和用户数据**，再冻结具体函数名。这样可以用同一个样包验证桌面、试验台和独立 Dock，避免三边各自实现一套看似相同的 API。
