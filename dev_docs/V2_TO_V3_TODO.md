## 2026-09-27：网页场景优先的路线调整（设计草案）

此前的分项清单仍用于追踪需求与技术风险，但其顺序不再直接代表新 v3 的实施优先级。用户已确认：Dock 是否随 Desk 改变不做成开关；每个对象分别决定是否跨 Desk 保留、保留后怎样响应 Desk。创作者可定义视觉过渡，Dext 提供默认动画；图片/视频、图标、Widget 与按钮进入统一的 HTML 场景运行逻辑。**普通用户仍应能通过 Dext 可视化编辑器完成简单 Room，不必写 HTML 或使用 AI**；高级作者可直接制作 HTML，两个入口通向同一 v3 运行契约。本节只调整**设计和验证的先后关系**，不改变 [ROADMAP.md](ROADMAP.md) 当前唯一下一项，也不表示 v3 已开工。

| 顺序 | 先得到什么结果 | 必须回答的核心问题 |
|---|---|---|
| 1. 定运行语义与两种创作入口 | 一页可讨论的 Room/Desk 状态、对象生命周期和切页契约，以及简单 Room 的无代码创作边界 | 固定 Dock、变形仪表盘、逐 Desk 内容能否用一套规则表达？普通用户在编辑器里最少需要哪些操作？ |
| 2. 做最小场景验证 | 一个可丢弃的浏览器试验样例，同时包含无代码可配置的图片/视频 Room、固定 Dock，以及作者自定义变形仪表盘；模拟 Dext 图标/普通 Widget 随 Desk 运动 | 两种创作方式能否共用一个网页舞台、Desk 状态、默认/自定义动画、占用和输入规则？ |
| 3. 冻结作品与作者契约 | v3 作品清单、官方模板参数、按钮/动作、状态与过渡 API、占用区和本机绑定边界；研究可选的作者游戏版 XAML 与数据槽声明；无共享 Room HTML 的最小作品也能说明 | 编辑器怎样生成简单 Room？进阶作者怎样声明对象与按钮？Dext 怎样发现、预览和校验？哪些数据随 Room 分享？游戏版 XAML 可接受什么受限语法？ |
| 4. 建统一桌面运行时 | 真实桌面使用持续的 HTML 宿主，图片/视频作为素材，用户图标与作者画面参加同一过渡 | 作者画面、Dext 图标/Widget、按钮动作和响应式布局能否在同一 Desk 状态机下稳定收敛？ |
| 5. 打通 Dext 编辑与创作 | Dext 列出所有声明按钮，预览定位并配置动作；试验台、AI 模板、导入/保存/分享使用同一契约 | 作者作品能否从创作、调试到用户绑定与正式应用走完闭环？ |
| 6. 接系统呈现通道与收口 | 在桌面场景模型稳定后接入置顶/自动隐藏/工作区占位的 Windows 宿主，并单独验证作者 XAML 驱动的游戏内只读 Dock 覆盖，再验收 v3 全链 | 一个固定游戏 Widget 宿主能否安全加载作者 XAML；与桌面 Dock 如何同步；在选定游戏中是否稳定显示；哪些旧 Core 模块需替换；何时停用 v2？ |

原生 Dock 的 AppBar、前台判断和窗口命中仍是独立的高风险研究，需在正式承诺第 6 步前验证；游戏内覆盖是另一个呈现通道，不能因游戏目标就推定必须全量重写 Core。先验证 Dext 状态/数据能否供两个呈现后端消费，再决定需要替换的 Lively 模块；这些系统层选择**不应反过来决定**桌面网页内固定 Dock 与变形仪表盘的对象模型。下方原第 0–6 节保留为需求/风险明细，待运行语义与首个场景验证后再拆成可独立验收的 ROADMAP 工作包。

**编辑范围边界（2026-09-27 修正）：**保留节点式路线图。现有界面已经有 Desk 节点、切换连线和转场设置；这些外形不构成 v3 新方案，也不必为了“新概念”全部重做。Dext 的简单编辑器主要服务照片/视频 Room，负责选背景、加 Desk、设置默认图标/模板 Dock 和基础切换；不需要可视化制作汽车仪表盘式连续推近、角色变化或复杂数据联动。需要校正的是转场连线背后的 v3 运行语义，以及试验台/真实桌面是否一致。第三方 HTML Room 至少可预览、发现声明按钮、绑定个人目标和展示作者公开的配置项；不承诺将任意 HTML 反向解析成可拖拽模板。具体 UI 改动逐项设计，不预设推翻当前路线图。

**Dock 外观→交互→Desk 方向（用户于 2026-09-27 确认）：**照片/视频 Room 的路线图保留 Desk 节点和切页连线，另以 Dock 外观、Dock 交互、Desk 组成组合链。创意工坊 Dock 模板自带作者定义的可点击区、数据展示槽位及其响应式位置；用户在交互节点配置点击动作，并按 Desk 选择每个槽位的数据类型，不重新绘制区域。例：同一左中右外观，Desk 1 显示 CPU／时间／GPU，Desk 2 显示倒计时／时间／日期。候选图形是一套外观连接两个交互配置，分别连接对应 Desk。个人应用绑定和倒计时等个人值留在本机。复杂仪表盘的连续推近仍由 HTML 作者完成，不要求路线图表达完整动画。组合线与 Desk 切页线的语义需明确区分。

**2026-09-28 连线方案定论：**两个 Desk 内容完全相同时共用 Dock 交互配置，且默认就相同；某 Desk 要差异时，点击通往它的连接线上的“＋”，在属性框中添加该 Desk 改动的属性。连线只保存这些差异，未填写的部分继续继承共享值；删除差异字段即恢复继承。上一段“两套交互配置分别连接”的候选图形不再是默认方案。

**游戏版作者内容（2026-09-27 候选，2026-09-28 推迟到基础版之后）：**用户希望游戏内能显示可定制外观的只读性能监控，而不只是文字/数字；XAML 可以绘制形状、图片和动画，但 Game Bar 宿主加载作者外观、实时数据和目标游戏中的表现未验证。先完成 v3 基础桌面能力，再把游戏覆盖作为后续版本的独立研究；若只得到简单数字显示，用户倾向排除该功能。若将来验证并立项，作者可为同一 Room 另交游戏外观及资源，游戏视图独立于桌面 Dock 模板；作者未提供时游戏中不显示 Dext 覆盖。数据配置是否共用，届时再定。

## Dext Core v3：在 Lively fork 上改写的设计计划（2026-09-27 草案）

**目标理解：**继续使用仓库中 Dext 自带的 Lively fork 作 Windows 桌面底座，逐步把运行中心改成 Dext 自己的 Room/Desk、个人绑定、权限和多呈现通道；保留有价值的 WorkerW、显示器、WebView2 Player、进程托管等基础。这里的“改写”是替换产品规则和模块边界，不以一次性全局改名或从零重造 Windows 桌面承载为交付目标。此节是讨论计划，不是已开工的 ROADMAP 工作包。**2026-09-28 确认：产品尚未上线，v3 不承担 v2 Room 或 Lively 原生非 Room 壁纸作品的兼容与迁移；v3 支持哪些内容能力另行逐类确认。**

**路径比较：**只做名称/程序集替换能改善表面身份，但解决不了 Room/Desk 状态仍在网页及多宿主不同步；完全从零实现 WorkerW、显示器、Player 与生命周期会重新承担已有的系统边界和回归风险。建议在现有 fork 内逐步建立 Dext 状态与宿主边界，确认替代链后再清理旧 Lively 类型和命名。这样每步都可与当前可运行产品比较并单独验收。

| 阶段 | 独立可验证的结果 | 为什么按此顺序 |
|---|---|---|
| 0. 盘点与风险样例 | 列出现有 Dext 真正依赖的 Core/Player 路径、旧 Lively 类型与发布资产；用一份 v2 Room 固定启动、切页、重启、退出的基线；隔离验证顶层 Dock 窗口 | 先找出要保留的桌面行为；游戏 Widget/XAML 原型推迟到基础版之后 |
| 1. 定 Dext 运行契约 | 定义一次 Room 安装/会话、Desk ID、切换请求与最终状态、修订号、个人绑定 ID、数据快照、能力与失败结果；明确配置器、Core、桌面 Player、Dock 窗口和游戏视图各自只负责什么 | 当前 `currentDesk` 在网页里，而未来多个视图须同步；先统一权威状态再分拆宿主 |
| 2. 改出 Dext 状态核心 | 在现有 Core fork 内建立 Room/Desk 状态与事件服务，负责持久化/恢复、切换仲裁、前台/暂停策略与数据发布；v2 的壁纸 RPC 暂作适配入口；用模拟消费者验证迟到消息、重启和故障回退 | 先让 Dext 逻辑站稳，再让每种窗口接入，不同时替换全部渲染和 Windows 宿主 |
| 3. 改桌面 Player 与受控动作 | WebView2 Player 继续承载 WorkerW 桌面，接 v3 持续 HTML 场景；切页由桌面视图请求、Core 确认，动画结果回报；个人目标和敏感动作只传绑定 ID，经 Core 校验执行 | 桌面是主体验，也是 Dock/游戏视图的数据与过渡基线 |
| 4. 加普通软件前的 Dock | Core 托管独立顶层 HTML 窗口；接同一 Room/Desk 快照；分别验收自动隐藏覆盖普通最大化、AppBar 常驻占位、全屏抑制和崩溃恢复 | 复用状态核心，但窗口层级、焦点、工作区是独立 Windows 行为 |
| 5. 游戏版只读视图（后续候选，不属 v3 基础版） | 基础版完成后再研究可定制游戏监控外观；若值得纳入，才讨论作者内容格式、只读数据、原生宿主与独立节点 | 这是另一种呈现后端；不以桌面 v3 的完成依赖它 |
| 6. 收口旧 Lively 路径 | v3 创建、导入、预览、应用、重启恢复、分享、卸载均通过 Dext 契约后，再删不需要的播放器、壁纸类型、旧 RPC/设置/名称；逐项确认发布包和本机开发数据未被误删 | 无兼容承诺；清理时检查仍被 v3 复用的代码和运行资产，避免破坏可用底座 |

**建议的模块界面，而非最终类名：**`RoomSession` 保管作品与 Desk 权威状态；`DextActionService` 管理绑定与动作授权；`SystemContext` 提供前台窗口/显示器/电源等事实；`DesktopHost`、`DockWindowHost`、`GameOverlayHost` 是三个消费者。壁纸播放暂停和 Dock/游戏可见性使用各自策略，不能把旧 `Playback` 的“被最大化窗口覆盖”直接当游戏判断。游戏版 XAML 节点的数据配置是否沿用各 Desk 的 Dock 交互节点，仍待用户确认。

**工作包拆分原则：**阶段 0 的原生实验与阶段 1 的契约可以各自验收；阶段 2–6 再按每个独立结果拆 ROADMAP ID、worktree、分支和验收卡。任何迁移/删除都放在确认新链可恢复之后。当前 ROADMAP 唯一下一项不因本讨论自动改变。

**路线图补充（用户确认）：**Room 作者单独添加游戏内 Dock XAML，不把它强制捆进可下载的 Dock 外观模板；在路线图中设独立节点。该节点与现有 Dock 交互节点、Desk 节点的连线和数据配置关系待设计，不能预设游戏版复用桌面版的逐 Desk 数据设置。游戏节点只负责显示，不带点击动作。

## v3 到位时应能看到什么

普通用户不写代码、不调用 AI，也能在 Dext 中添加 Desk、选择图片/视频背景和默认呈现，预览并应用一个简单 Room。进阶作者或 AI 能制作自包含的 HTML Room 文件夹，导入后在试验台预览、修正错误、绑定本机应用，再应用到真实桌面。两条创作路径使用同一 v3 运行契约。作品可选择有/无常驻 Room HTML；同一 Dock 可跨 Desk 不变，其他共享对象可随 Desk 连续变形，逐 Desk 内容可随对应画面进出。桌面应用图标仍由 Dext 管理，但参与统一 HTML 场景的视觉过渡。占用区会阻挡普通图标和 Widget，受控按钮能切页/启动绑定应用。若作品启用独立 Dock，用户可在“自动隐藏覆盖最大化窗口”和“常驻占位让最大化窗口避让”之间选择；游戏中桌面 Dock 窗口隐藏，另研究是否以只读覆盖通道显示完整 Dock 外观。

## 原分项清单（需求与风险明细，非新路线顺序）

### 0. 先验证关键架构风险

- [ ] 将现有 `Playback` 的暂停策略与 Dock 显示策略分开验证：普通最大化不能因 `IsZoomed` 被当游戏隐藏；比较前台事件与定时复核，不直接复用 `AppFullscreenPause`。
- [ ] 记录 Player SDK/Runtime、.NET Framework 4.7.2 与 Core .NET 9 的构建边界；原生窗正常输入不混入 WorkerW 的 RawInput 转发。透明外观和原生毛玻璃分别判定；局部点击穿透仅在发现矩形窗口挡住实际操作时研究。

- [ ] 做一个最小 v3 连续场景实验：同一作品有两个 Desk，常驻汽车仪表盘在 Desk 1 是底部 Dock，切页时不重建并连续推近，到 Desk 2 成为可交互的全屏主画面；两侧 Dext 图标/普通 Widget 随所属 Desk 区域滑动，反向切换可回到原形态。再用没有 Room HTML 的作品验证 Desk HTML 能独立构成画面。
- [ ] 验证视觉控制契约：作者自定义切页动画与 Dext 默认动画都能驱动同一 Desk 状态机；图标/普通 Widget 与作者场景同步，动画失败或超时能收敛到确定的 Desk。作者动画不增加本机系统权限。
- [ ] 量出 Room/Desk 实例生命周期：切页、过渡取消、作品切换、Player 重建与 `pagehide` 后，旧实例不能再收数据或占用区；常驻实例在同一 Room 的 Desk 切换中不重建。给跨窗口状态消息加 revision，验证迟到消息不会回滚画面。
- [ ] 单独试验原生 Dock 宿主：Core 管理的 HTML 窗口在普通最大化软件上方展开；收起后只留边缘触发条；常驻模式能让最大化窗口避让；进入全屏游戏时 Dock 和触发条都隐藏。验证任务栏冲突、按钮输入、窗口矩形是否挡住实际操作、焦点、DPI、退出恢复。该实验只判断路径是否可靠，不先定最终外观。
- [ ] 原生试验先用当前 WinForms WebView2 的矩形窗口验证 Dock 画面与按钮；实测受阻再比较其他宿主。验证 AppBar 的 `ABM_NEW → ABM_QUERYPOS → ABM_SETPOS → ABM_REMOVE`、`ABN_POSCHANGED`、同边任务栏、多屏坐标；对照系统自动隐藏 AppBar 与自管边缘触发窗。记录可复现测试矩阵及失败截图/日志，再选宿主技术。
- [ ] 分别验证标准最大化、F11、无边框游戏和独占全屏；评估 `ABN_FULLSCREENAPP` 与前台窗口事件组合的误判、漏判，明确是否需要用户覆盖规则。检查游戏进入时 AppBar 占位如何撤销及恢复。
- [ ] 试验 HTML 动态上报多块占用区与动作命中区，验证屏幕尺寸改变后图标和普通 Widget 都不能落进占用区，透明间隙仍可使用。
- [ ] 设计一份只含矩形/视口/revision 的共享几何模块，分别接到配置器自动摆放、真实桌面图标拖动、普通 Widget 拖动/放置；用同一组场景比较结果。测试伪造来源、越界/过大/过多区域、过期 revision、屏幕缩小无空位。

### 1. 冻结 v3 作品契约

- [ ] 定义唯一 v3 清单/Schema：Room 与 Desk HTML 入口、start/switch/idle、组件、资源、能力申请、默认 Desk、版本和可选常驻层。提供“有 Room HTML”和“无 Room HTML”两个最小样包。
- [ ] 定义本机用户数据与可分享作品的边界：应用绑定、图标位置、权限、待办数据和运行态如何保存；作者包不携带本机程序路径、用户隐私或授权结果。
- [ ] 定义授权与可执行资源摘要/安装快照的关系，避免只哈希 room.json；创作预览与正式应用的授权策略区分，本机布局变化不应无意改变作品内容身份。
- [ ] 定义安全的组件存储 API；验证现有 opaque-origin sandbox 下待办持久化，不通过直接放开同源权限绕过隔离。
- [ ] 明确“键盘切页”需要桌面活动范围还是系统全局组合键；后者补 Core 热键、冲突提示和全屏游戏抑制。
- [ ] 定义组件类型与权限边界：普通 Widget、具有导航/绑定应用动作的 Dock 类组件、常驻 Room 组件分别可见什么；同一作者项目里的特权与普通 HTML 怎样隔离。
- [ ] 对现有网页→Player→Core 的通用 `msg_launch` 路径做 v3 威胁审查，设计 `bindingId` 启动命令和宿主侧用户手势/授权/来源复核；不能把 HTML 传来的 `target/args/workdir` 当成 v3 应用绑定。
- [ ] 定义响应式坐标、占用区/命中区上报协议、限制和失败回退；明确常驻组件跨 Desk 的状态/内容接口及全局+Desk 应用合并规则。
- [ ] 定义独立 Dock 的 Windows 模式由谁选择和存储、哪些作品入口能用于独立窗口，以及工作区保留所需的边缘矩形约束。

### 2. 建立最小可用 v3 运行时

- [ ] 宿主可读取 v3 Room，挂载/销毁 Desk HTML，持续挂载可选 Room HTML，并正确更新当前 Desk、暂停、过渡和资源路径；图片/视频可作为 HTML 作品素材。
- [ ] 桌面图标作为统一 HTML 场景的一部分随所属 Desk 运动；Dext 继续负责个人绑定、拖动/保存语义与启动授权。作者对图标 DOM 的可定制边界按验证后的契约工作。
- [ ] 受控桥把时间、硬件、媒体等现有数据送给正确实例；只接受已授权组件的导航与本机绑定应用动作，且动作需要可信用户输入。普通 Widget 尝试同一动作必须被拒绝。
- [ ] 由受信任宿主接收动作输入；拒绝把 iframe 自报 isTrusted、token 或来源正确当成真实手势。验证 Room 全屏 iframe 空白不挡图标、表单和按钮可正确接收输入。
- [ ] 占用区同时进入配置器自动放置与真实桌面图标/Widget 布局；尺寸变化、Desk 切换、组件失效和无合法位置都有可见的回退结果。

### 3. 做成可使用的原生 Dock 模式

- [ ] 由 Core 管理独立 Dock HTML 宿主，与桌面 Player 同步 Room/Desk 状态和用户绑定；配置器关闭后 Dock 仍正常运行。
- [ ] 在 Core 壁纸 Player 生命周期之外新增 Dock 专用窗口角色与 IPC；确认它不进入 `WinDesktopCore` 的 WorkerW `SetParent` 路径。Dock 进程退出、配置器退出、Core 重启与作品切换均有明确的重建/清理结果。
- [ ] 自动隐藏模式：边缘触发条、悬停展开到最大化窗口上方、离开收起；按钮可点击，窗口矩形不挡住实际需要操作的位置，工作软件不被无故抢焦点。
- [ ] 用原生状态机表达关闭、收起、展开、真全屏抑制；触发条与 Dock 联合鼠标范围加收起延时，并验证触边展开时普通最大化软件仍保持工作区全屏。
- [ ] 常驻占位模式：贴边工作区协商、最大化窗口避让、任务栏变动处理、退出时释放占位；呈现给作者的占位限制要与 HTML 预览一致。
- [ ] 全屏时先测试保留 AppBar 注册并隐藏/降 Z 顺序，仅在证据需要时增加临时释放占位；覆盖 Explorer 重启、锁屏恢复、异常退出及延迟触边回调。
- [ ] 明确 AppBar 只保留贴边矩形；在试验台标出系统占位边带和 HTML 实际画面两个范围，避免作者误以为仪表盘圆弧会形成同形状避让。
- [ ] 全屏游戏模式：无论之前是哪一种 Dock 模式，进入游戏时 Dock 与触发条完全隐藏；退出后恢复。用真实窗口化/无边框/独占游戏与 Alt-Tab 验证检测边界。
