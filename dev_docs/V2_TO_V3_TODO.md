> 2026-09-25 建立。此文件是设计阶段的迁移清单，**不是**当前分支的 [TODO.md](TODO.md)、唯一开发顺序的 [ROADMAP.md](ROADMAP.md)，也不表示 v3 已开工。实施时再把可独立验收的事项写成 ROADMAP 工作包，按 [WORKFLOW.md](WORKFLOW.md) 建分支、worktree 和验收卡。
> 产品目标、已确定体验与实现候选见 [V3_IDEAS.md](V3_IDEAS.md)；连续网页与 Desk 切换的候选运行契约见 [V3_RUNTIME_MODEL.md](V3_RUNTIME_MODEL.md)。现有 v2 Room 可在 v3 成熟后删除重做；此清单不要求自动迁移旧 Room，也不授权现在删除用户数据。

## v3 到位时应能看到什么

用户或 AI 能制作一个自包含的 HTML Room 文件夹，导入后在试验台预览、修正错误、绑定本机应用，再应用到真实桌面。作品可选择有/无常驻 Room HTML；切 Desk 时共享外形可换内容，桌面应用图标仍由 Dext 管理。占用区会阻挡普通图标和 Widget，受控按钮能切页/启动绑定应用。若作品启用独立 Dock，用户可在“自动隐藏覆盖最大化窗口”和“常驻占位让最大化窗口避让”之间选择；全屏游戏时 Dock 完全隐藏。

## 按依赖顺序的待办

### 0. 先验证关键架构风险

- [ ] 将现有 `Playback` 的暂停策略与 Dock 显示策略分开验证：普通最大化不能因 `IsZoomed` 被当游戏隐藏；比较前台事件与定时复核，不直接复用 `AppFullscreenPause`。
- [ ] 记录 Player SDK/Runtime、.NET Framework 4.7.2 与 Core .NET 9 的构建边界；原生窗正常输入不混入 WorkerW 的 RawInput 转发。透明外观和原生毛玻璃分别判定；局部点击穿透仅在发现矩形窗口挡住实际操作时研究。

- [ ] 做一个最小 v3 连续场景实验：同一作品有两个 Desk，常驻汽车仪表盘在 Desk 1 是底部 Dock，切页时不重建并连续推近，到 Desk 2 成为可交互的全屏主画面；两侧 Dext 图标/普通 Widget 随所属 Desk 区域滑动，反向切换可回到原形态。再用没有 Room HTML 的作品验证 Desk HTML 能独立构成画面。
- [ ] 量出 Room/Desk 实例生命周期：切页、过渡取消、作品切换、Player 重建与 `pagehide` 后，旧实例不能再收数据或占用区；常驻实例在同一 Room 的 Desk 切换中不重建。给跨窗口状态消息加 revision，验证迟到消息不会回滚画面。
- [ ] 单独试验原生 Dock 宿主：Core 管理的 HTML 窗口在普通最大化软件上方展开；收起后只留边缘触发条；常驻模式能让最大化窗口避让；进入全屏游戏时 Dock 和触发条都隐藏。验证任务栏冲突、按钮输入、窗口矩形是否挡住实际操作、焦点、DPI、退出恢复。该实验只判断路径是否可靠，不先定最终外观。
- [ ] 原生试验先用当前 WinForms WebView2 的矩形窗口验证 Dock 画面与按钮；实测受阻再比较其他宿主。验证 AppBar 的 `ABM_NEW → ABM_QUERYPOS → ABM_SETPOS → ABM_REMOVE`、`ABN_POSCHANGED`、同边任务栏、多屏坐标；对照系统自动隐藏 AppBar 与自管边缘触发窗。记录可复现测试矩阵及失败截图/日志，再选宿主技术。
- [ ] 分别验证标准最大化、F11、无边框游戏和独占全屏；评估 `ABN_FULLSCREENAPP` 与前台窗口事件组合的误判、漏判，明确是否需要用户覆盖规则。检查游戏进入时 AppBar 占位如何撤销及恢复。
- [ ] 试验 HTML 动态上报多块占用区与动作命中区，验证屏幕尺寸改变后图标和普通 Widget 都不能落进占用区，透明间隙仍可使用。
- [ ] 设计一份只含矩形/视口/revision 的共享几何模块，分别接到配置器自动摆放、真实桌面图标拖动、普通 Widget 拖动/放置；用同一组场景比较结果。测试伪造来源、越界/过大/过多区域、过期 revision、屏幕缩小无空位。

### 1. 冻结 v3 作品契约

- [ ] 定义唯一 v3 清单/Schema：Room 与 Desk HTML 入口、start/switch/idle、组件、资源、能力申请、默认 Desk、版本和可选常驻层。提供“有 Room HTML”和“无 Room HTML”两个最小样包。
- [ ] 定义本机用户数据与可分享作品的边界：应用绑定、图标位置、权限、待办数据和运行态如何保存；作者包不携带本机程序路径、用户隐私或授权结果。
- [ ] 定义授权与可执行资源摘要/安装快照的关系，避免只哈希 room.json；创作预览与正式应用的授权策略区分，本机布局变化不应无意改变作品内容身份。
- [ ] 定义安全的组件存储 API；验证现有 opaque-origin sandbox 下待办持久化，不通过直接放开同源权限绕过隔离。
- [ ] 明确“键盘切页”需要桌面活动范围还是系统全局组合键；后者补 Core 热键、冲突提示和全屏游戏抑制。
- [ ] 定义组件类型与权限边界：普通 Widget、具有导航/绑定应用动作的 Dock 类组件、常驻 Room 组件分别可见什么；同一作者项目里的特权与普通 HTML 怎样隔离。
- [ ] 对现有网页→Player→Core 的通用 `msg_launch` 路径做 v3 威胁审查，设计 `bindingId` 启动命令和宿主侧用户手势/授权/来源复核；不能把 HTML 传来的 `target/args/workdir` 当成 v3 应用绑定。
- [ ] 定义响应式坐标、占用区/命中区上报协议、限制和失败回退；明确常驻组件跨 Desk 的状态/内容接口及全局+Desk 应用合并规则。
- [ ] 定义独立 Dock 的 Windows 模式由谁选择和存储、哪些作品入口能用于独立窗口，以及工作区保留所需的边缘矩形约束。

### 2. 建立最小可用 v3 运行时

- [ ] 宿主可读取 v3 Room，挂载/销毁 Desk HTML，持续挂载可选 Room HTML，并正确更新当前 Desk、暂停、过渡和资源路径；图片/视频可作为 HTML 作品素材。
- [ ] 桌面图标作为统一 HTML 场景的一部分随所属 Desk 运动；Dext 继续负责个人绑定、拖动/保存语义与启动授权。作者对图标 DOM 的可定制边界按验证后的契约工作。
- [ ] 受控桥把时间、硬件、媒体等现有数据送给正确实例；只接受已授权组件的导航与本机绑定应用动作，且动作需要可信用户输入。普通 Widget 尝试同一动作必须被拒绝。
- [ ] 由受信任宿主接收动作输入；拒绝把 iframe 自报 isTrusted、token 或来源正确当成真实手势。验证 Room 全屏 iframe 空白不挡图标、表单和按钮可正确接收输入。
- [ ] 占用区同时进入配置器自动放置与真实桌面图标/Widget 布局；尺寸变化、Desk 切换、组件失效和无合法位置都有可见的回退结果。

### 3. 做成可使用的原生 Dock 模式

- [ ] 由 Core 管理独立 Dock HTML 宿主，与桌面 Player 同步 Room/Desk 状态和用户绑定；配置器关闭后 Dock 仍正常运行。
- [ ] 在 Core 壁纸 Player 生命周期之外新增 Dock 专用窗口角色与 IPC；确认它不进入 `WinDesktopCore` 的 WorkerW `SetParent` 路径。Dock 进程退出、配置器退出、Core 重启与作品切换均有明确的重建/清理结果。
- [ ] 自动隐藏模式：边缘触发条、悬停展开到最大化窗口上方、离开收起；按钮可点击，窗口矩形不挡住实际需要操作的位置，工作软件不被无故抢焦点。
- [ ] 用原生状态机表达关闭、收起、展开、真全屏抑制；触发条与 Dock 联合鼠标范围加收起延时，并验证触边展开时普通最大化软件仍保持工作区全屏。
- [ ] 常驻占位模式：贴边工作区协商、最大化窗口避让、任务栏变动处理、退出时释放占位；呈现给作者的占位限制要与 HTML 预览一致。
- [ ] 全屏时先测试保留 AppBar 注册并隐藏/降 Z 顺序，仅在证据需要时增加临时释放占位；覆盖 Explorer 重启、锁屏恢复、异常退出及延迟触边回调。
- [ ] 明确 AppBar 只保留贴边矩形；在试验台标出系统占位边带和 HTML 实际画面两个范围，避免作者误以为仪表盘圆弧会形成同形状避让。
- [ ] 全屏游戏模式：无论之前是哪一种 Dock 模式，进入游戏时 Dock 与触发条完全隐藏；退出后恢复。用真实窗口化/无边框/独占游戏与 Alt-Tab 验证检测边界。

### 4. 创作试验台与 AI 交付

- [ ] 配置器能导入 AI 生成的本地 v3 文件夹，先隔离检查，再显示缺文件、路径、能力和脚本错误；确认后才写入 Room 库。
- [ ] 试验台预览 Desk、常驻 Room、独立 Dock 的两种窗口模式及多尺寸画面；显示占用区、命中区、图标/Widget 冲突和能力模拟。预览使用生产协议与布局规则。
- [ ] 给外部 AI 提供版本化模板、类型/API 文档、正反例、可运行示例和检查命令；修改文件后能快速刷新。普通 Widget 是否仍可在桌面编辑模式拖动，在此阶段做体验决定。
- [ ] 作者 HTML 用同一契约声明所有按钮的稳定 ID、名称、所属 Desk/Room、可分享默认动作和运行中的命中区域。Dext 编辑器提前列出全部按钮、按 Desk 定位/高亮，并在统一入口中允许用户覆盖动作及绑定本机目标；覆盖值不回写 Room。未配置、Desk 切换和权限拒绝可在试验台模拟。不同动作在系统内部按各自权限和参数校验；“退出 Dext”的范围与确认语义先定义再纳入动作清单。

### 5. 完成保存、应用与分享闭环

- [ ] v3 的创建、读取、编辑、另存、预览、应用、zip 导入导出使用同一严格验证器；离线资源、权限、路径穿越、链接、重复项和解压限制不倒退。
- [ ] 真实桌面和试验台显示同一作品结果；切 Room/Desk、Core 重启、配置器退出后，图标、常驻 HTML、Widget、Dock 模式与授权状态按契约恢复。
- [ ] 以一份 AI 生成的“游戏/生活双 Desk 汽车仪表盘”作品做端到端人工验收，覆盖两个 Dock 窗口模式和无 Room HTML 的另一份作品。

### 6. v2 收口

- [ ] 只有 v3 全链验收完成并得到用户明确同意后，再决定停用 v2 的创建/应用/导入和清理旧演示 Room；不把“无需迁移”理解为现在自动删除用户文件。
- [ ] 更新 [README.md](README.md)、[PROJECT.md](PROJECT.md)、正式模型与作者协议，让 v3 成为唯一现行口径；旧 v2 文档标为历史，避免 AI 继续按 v2 生成。
- [ ] 完成分支验收、合并和清理后，把这份草案中已实现的项标明对应工作包；开发状态仍只认 ROADMAP/TODO/验收卡。

## 尚需用户决定

- 独立 Dock 的“自动隐藏/常驻占位”是 Dext 全局偏好、逐 Room 偏好，还是两者组合？
- 更换 Room 后桌面应用图标位置和绑定按用户全局、Room、Desk 中哪一级保留？
- 同一应用同时出现在全局和当前 Desk 列表时，显示一次还是两次？
- 普通 Widget 的移动只在试验台进行，还是保留桌面编辑模式直接拖动？
- 占用区上报失效或屏幕缩小导致无空位时，图标和 Widget 如何回退？
- 生活 Desk 的待办、倒计时等可变数据由哪种本机存储和权限提供？
