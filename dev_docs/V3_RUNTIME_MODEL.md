# Room v3 运行逻辑讨论稿

> 2026-09-26。用于先把 Dext Room 的运行语义说清，再设计作品格式与作者 API；**不是现行 v2 契约，也不是已批准的 v3 Schema 或实现计划**。产品背景见 [V3_IDEAS.md](V3_IDEAS.md)，作者 API 问题见 [V3_API_NOTES.md](V3_API_NOTES.md)。

> **新方向（同日讨论，尚未冻结）：**用户希望把可见桌面的底层组织进一步统一到网页场景：应用图标也处在 HTML 场景中，图片/视频壁纸成为 HTML 的素材，而不是让各内容类型各走一套切页运行逻辑。下面仍需区分“同一网页画面”与“作者脚本拥有全部宿主权限”。

## 1. 要保证的体验

1. 一个 Room 能表现为**一张持续运行的网页/逻辑画布**。Desk 是这张画布中的视角或状态；用户切 Desk 时，不必卸载整张网页再打开另一页。
2. 普通应用图标和 Widget 属于相应 Desk 的画面区域，翻页时随该区域移动。跨 Desk 的共享元素可独立变化：例如同一个汽车仪表盘在 Desk 1 是底部 Dock，切到 Desk 2 时连续推近，成为可交互的主背景，反向切换再缩回去。
3. 背景、交互、Dock 是**代码中可变化的呈现角色**，不是 PS 式固定物理层。按钮可画在背景或 Dock 内；同一对象的角色可随 Desk 改变。
4. Room 分享 HTML 外观、布局、可绑定入口和经允许的通用 Dext 操作；具体应用、文件、网址绑定以及个人图标皮肤属于 Dext 本机数据。启动入口可表现为默认图标、换肤/自绘图标，或作者在画面任意位置设计的按钮；现有默认图标桌面仍可作为不自绘时的呈现。
5. Desk 导航、个人目标执行、权限、图标/Widget 放置和 Windows 窗口行为由 Dext 掌握。作者 HTML 控制画面与过渡的表现，不直接修改 Dext 的权威 Desk 状态。

“一张网页”描述**运行连续性**，不要求作品只有一个 HTML 文件，也不强制使用 HTML `<canvas>`。常驻场景、Desk 内容和可复用组件可由多个文件组成。

## 2. 一个 Room 运行时有哪些对象

| 对象 | 生命周期与职责 |
|---|---|
| Dext 桌面宿主 | 作品使用期间持续存在；维护权威 Room/Desk 状态、导航、用户内容、能力校验和窗口消息 |
| Room 共享场景（作者可选） | 同一 Room 的 Desk 切换期间持续存在；容纳会跨 Desk 变形或保持运行的元素，例如汽车仪表盘 |
| Desk 场景 | 每个 Desk 的主背景与局部 HTML 内容；Desk ID 由该 Room 定义，名称和数量不由 Dext 预设 |
| Desk 用户内容 | Dext 管理的应用图标、普通 Widget、用户绑定入口；作为网页画面的一部分，位置属于某个 Desk 的视觉坐标系，跟随该 Desk 过渡。它们的本机目标和权限仍由 Dext 管理 |
| 共享元素 | 属于 Room 共享场景，可按当前 Desk 呈现为 Dock、背景或其他角色；切页时不因旧 Desk 离开而重建 |
| 原生 Dock 窗口 | 仅当 Dock 要显示在普通 Windows 软件前时使用；它是另一窗口，不是桌面网页的 CSS 顶层 |

**交互层的候选语义（2026-09-26）：**凡是接收用户操作的图标、壁纸按钮、Widget 控件、切页键等，都可归为交互层的内容。它描述元素的交互职责，不要求它们搬到同一个 DOM 容器：一个按钮可以视觉上嵌在背景或 Dock 内。按钮能否启动应用由 Dext 授权和用户绑定决定，不靠它所在的图层自动取得权限。

**启动入口的候选模型：**Dext 本机保存一个用户目标（例如 Word 的启动信息，可能是路径或应用标识）及其绑定 ID；Room 只提供可见入口。入口至少可有两种呈现：① 带图标的入口，图标可用原样、个人皮肤或作者自绘；② 作者画的任意 HTML 按钮/区域，由使用者将其绑定到本机目标。两种呈现最终都提交绑定 ID 给 Dext 执行动作。用户口中的“路径 + 按钮”不意味着真实路径写进 Room HTML 或分享包。**两类入口可在同一 Desk 同时存在，也可指向同一目标**；具体编辑控件与位置保存规则仍待讨论。

**用户确认的叠放场景：**情景化背景上预留多个作者按钮，使用者分别配置目标；使用者还可以在它们上方放普通应用图标。背景按钮与上方图标同属可交互内容，却处在不同视觉深度。故“交互层”不能解释成唯一一张盖满背景的固定平面；视觉叠放、可点击范围及放置占用要分别表达。按此前占用区决定，按钮所在的保留区域应阻止普通图标和 Widget 被放到其上，具体边界由作者声明并经 Dext 校验。

**用户确认的绑定流程（2026-09-26）：**使用者进入 Dext 编辑按钮功能，不在桌面上逐个点击按钮设置。Dext 需要先发现当前作品各 Desk/共享场景中作者提供的按钮，再在编辑界面列出、定位和配置；一个按钮未配置动作时也应能被识别。候选作者契约是统一声明按钮的稳定 ID、所属范围、供编辑器显示的名称、当前/默认动作，并把运行中的 HTML 元素/命中区域关联到该 ID。Dext 据此枚举和在预览中高亮；不能仅靠扫描 `<button>`、CSS 或图片像素猜出哪些区域是按钮及其动作。按钮若随 Desk 或动画出现/隐藏，清单与当前可见位置要分开处理。

**按钮优先、动作随后（用户纠正）：**不要让作者或使用者先学习“启动按钮”“切页按钮”等不同按钮种类；它们先是同一种按钮，切 Desk、启动用户目标、媒体控制、作品内部交互或暂未分配功能是按钮的动作属性。默认应用图标也可理解为带图标外观、默认绑定应用启动动作的入口；其拖动/排布仍是独立布局行为。Dext 编辑器统一展示按钮，再展示和配置当前动作。不同动作需要的参数、授权与失败反馈可以在系统内部不同，不能因为 UI 统一就跳过权限检查。

**作者默认动作与用户覆盖（用户确认）：**作者分享的 Room 可以给按钮预设切 Desk 等不含个人目标的 Dext 动作；用户进入 Dext 后可把该按钮改配为另一种受支持的动作，包括打开自己的应用绑定。覆盖值保存在用户本机，分享包继续保留作者默认值且不携带个人路径。作者还提出“退出 Dext”可作为候选 Dext 动作；其具体退出范围、是否需要二次确认及恢复方式尚未定义，不能把 HTML 任意脚本直接映射为退出命令。

**统一运行规则建议：**Dext 宿主始终有持续运行的舞台；作者的共享 Room HTML 是可选的。只有各 Desk 内容的作品仍使用同一宿主切页流程；需要跨 Desk 严格连续变形的对象则放在持续存在的共享场景中。这样保留此前确定的“有 Room HTML / 无 Room HTML”两种创作方式，同时避免实现两套互不兼容的 Desk 状态机。

## 3. Desk 切换应发生什么

以下是**待讨论的运行顺序**，描述职责，不冻结函数名或动画 API。

| 阶段 | Dext 的责任 | 作者画面的责任 |
|---|---|---|
| 静止在 Desk A | 报告权威当前 Desk、用户绑定与受控数据；只允许 A 的可用入口接收动作 | 显示 A 的背景、交互内容和共享元素在 A 的形态 |
| 请求切 Desk B | 接收键盘或经授权的 HTML 按钮请求；校验目标、输入来源、当前是否允许切换，生成一次切换标识 | 不自行把 `currentDesk` 改成 B；等待宿主发出的切换意图 |
| 准备过渡 | 保证 A、B 两侧必要内容可同时绘制；确定图标/Widget 分属哪个 Desk；取得当前视口与布局 | 给出 A→B 的目标画面；共享元素保留原实例并准备 B 的形态 |
| 动画进行 | 让 A 的图标/Widget 随 A 区域离开、B 的随 B 区域进入；协调同一次过渡的输入、布局与超时 | 画出 Desk 区域移动和共享元素的连续变形，不用重新加载页面伪装连续性 |
| 提交 Desk B | 原子地把权威当前 Desk 改为 B；更新可执行动作、数据上下文和最终占用/点击区域；发出完成通知 | B 的布局和可交互状态稳定；仪表盘已成为 B 的背景/控件 |
| 中断或失效 | 明确回到 A 或落到 B，清理过期切换标识；旧消息不能覆盖新状态 | 停止上一段动画，画面与 Dext 的最终 Desk 一致 |

切换中不应同时启动两条互相争夺 DOM/图标的动画。反向输入是立即反转、排队还是暂时忽略，属于体验决定；无论哪种，宿主与 HTML 最后必须收敛到同一个 Desk。**切换状态、过渡标识和完成时机只能有一个权威来源。**

## 4. 画布、图层与占用

- 各 Desk 可以理解为同一逻辑画布上的区域/视角。Dext 默认图标和普通 Widget 不能固定在一个与 Desk 无关的视口叠层，否则翻页时会突然换位；它们要跟随所在 Desk 的画面运动。具体采用 DOM 容器、共享变换或别的渲染方式，待原型验证。
- 用户进一步希望图标本身也属于 HTML 场景。当前 v2 图标事实上已经由官方页面生成 HTML 节点，但作者背景 HTML 在独立沙箱 iframe 内，切页又会重挂内容；所以 v3 的变化重点是**让可见内容共用可连续变化的场景与运行契约**，不是简单把图标从原生控件改写成 HTML。
- 共享仪表盘不属于 Desk A 图标组；它持续存在，按 A/B 状态改变位置、尺寸、角色和可点击部分。因此“Dock 层→背景层”是同一对象的状态变化，不是把 DOM 从一个窗口搬到另一个窗口。
- 占用区阻挡普通图标和 Widget；可点击区决定谁接收输入，两者分别定义。作者可以标记 HTML 元素/区域，Dext 测量并校验。静止在 A/B 时各有有效布局；动画中建议暂停图标/Widget 的拖动与放置，避免一边移动一边重新求格。何时切换点击命中与能否在动画中点击，待试验。
- 屏幕尺寸改变时，作者的响应式 HTML 先得到新布局，Dext 再以同一视口版本更新占用与图标位置。不能让过期区域把图标推到旧坐标。

## 5. Dext 不在桌面前台时

用户倾向于 Dext 未处于可操作前台时**可能暂停 Desk 切换**。因此汽车仪表盘的连续推近只需先在 Dext 桌面内成立；不用把同一个 DOM 从盖在普通软件上的原生 Dock 窗口飞入桌面网页。普通最大化软件前的 Dock 自动隐藏/常驻占位、真正全屏游戏时隐藏，仍是独立的原生窗口运行逻辑。如何判定“桌面可操作”、已有动画遇到前台切换如何收尾，以及恢复后的 Desk 状态，需要实机验证后再冻结。

## 6. 作者至少要知道的运行契约

正式 v3 作者文档应能回答这些问题，AI 才能生成真正可运行的 Room：

1. 我在哪里声明 Room、Desk ID、共享场景、每个 Desk 的内容，以及某个元素在不同 Desk 的呈现状态？
2. 我怎样画一个切页按钮，按钮请求的是“下一 Desk”还是指定 Desk？Dext 拒绝或暂停切页时我会收到什么反馈？
3. 过渡由谁启动、谁决定时长/轨迹、何时算完成？Dext 图标怎样与作者的场景共用过渡，而不靠每帧把大量 DOM 坐标发过 IPC？
4. 我怎样给图标/Widget 留位置、怎样定义可点击元素？响应式缩放和切换动画中这些区域如何更新？
5. 我怎样声明用户可绑定的空按钮，以及通用 Dext 操作？导入别人分享的 Room 后，个人绑定缺失时画面怎样呈现？
6. 哪些组件可以持续存在、获得受控系统数据或执行动作？离开 Desk、暂停、切换 Room、Player 重建时怎样清理？

这些是**契约问题清单**，不是已经确定的函数名、manifest 字段或权限矩阵。

## 7. 与当前 v2 的关键差别及首个验证样例

当前 [renderDesk](../wallpapers/dext-room/main.js)在切页完成后重新挂载目标背景、Widget 和图标；[switchDesk](../wallpapers/dext-room/main.js)先搭目标 Desk 的 staging 画面再提交。现有结构可以做普通滑动切页，但它本身不能保证作者的同一个仪表盘 DOM 从 Dock 连续变成背景。v3 要把**持续运行的共享场景**和**随 Desk 运动的用户内容**定义为正式运行概念。

现有 HTML 背景/Widget 在 `sandbox="allow-scripts"` iframe 内，而 Dext 图标由父级宿主的 HTML 绘制。作者 iframe 内随意写一段 CSS 动画，**不会自动带动父级图标**。因此“同一网页”还需要决定图标与作者画面的组合边界：能否处于一个共同变换的场景中，同时保留应用绑定和动作校验。这个边界比动画 API 取什么名字更早需要验证。

首个原型应只验证：两个 Desk、一张持续运行的汽车仪表盘、A 的底部 Dock → B 的全屏背景及反向动画、两侧普通 Dext 图标随 Desk 滑动、静止后的占用区阻挡图标/Widget、按钮通过 Dext 导航。试验台与真实桌面使用同一过渡/几何逻辑；性能和原生窗口问题分别实测。这个样例验证运行模型，不代表 v3 其它功能已经完成。

## 8. 网页优先的统一渲染方向与待定边界

用户提出更大的 v3 方向：**可见桌面都朝 HTML 场景靠拢**。图片、视频作为网页素材；默认图标、用户皮肤、自绘按钮、普通 Widget 和 Dock 的桌面形态都能参与同一个连续画面。Dext 可以为不写复杂 HTML 的作品提供默认模板，因此“全面拥抱 HTML”不应使简单图片/视频 Room 难以制作。已沿用的运行选择是：一个持续运行的 Dext 宿主、可选的作者共享 Room 场景、任意数量的 Desk 内容，以及同一套 Desk 状态机。

**必须分开的两件事：**(1) 图标在网页里绘制并随作者画面运动；(2) 作者脚本是否能直接创建、移动或操作 Dext 图标节点。前者是用户希望的体验方向，后者涉及安全、拖动持久化和默认回退，目前未定。Dext 必须仍是本机应用绑定、用户数据、Desk 权威状态与特权动作的拥有者；作者作品可以控制外观，但不能因为同处一张网页就绕过授权。

用户进一步明确，图标启动和壁纸自定义按钮启动应使用**同一类交互入口及授权语义**。作品可以决定入口的外形和位置，Dext 提供默认图标并管理用户选择的图标皮肤、具体目标和执行。交互层只是便于作者组织这些入口的概念；具体可点击区域、占用区域及 `app.launch` 等能力仍要分别声明和校验。

过渡控制的候选是让作者定义画布/镜头的视觉变化，Dext 的图标和 Widget 跟随同一个场景运动；普通作品使用 Dext 提供的默认滑动。需要原型验证图标以何种受控 HTML 容器或渲染接口进入作者可布局的场景、跨沙箱如何同步、过渡进度由谁驱动，以及失效时如何回退。**原生顶层 Dock 窗口**仍是另一 Windows 窗口，不能仅靠统一桌面 HTML 解决其置顶和工作区占位。
